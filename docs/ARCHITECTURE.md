# Bath Dream — архитектура клиентского MVP

## Контуры

```
React Client
    |
    | VITE_API_URL
    v
Node API
    |
    +-- PRICE_BOOK (versioned calculation config)
    |
    +-- AUTH_ACCOUNT
    |     +-- OTP_CHALLENGE
    |     +-- SESSION
    |
    +-- CLIENT_PROFILE
    |
    +-- PROJECT
    |     +-- ORDER
    |           +-- DOCUMENT
    |           +-- PAYMENT
    |           +-- rooms / geometry
    |           +-- demolition selections
    |           +-- estimate rates
    |           +-- waste & logistics
    |
    v
SQLite
```

## Разделение ответственности

**AUTH_ACCOUNT** отвечает только за вход и подтверждение телефона/e-mail.

**CLIENT_PROFILE** содержит тип клиента и минимальные данные для клиентского кабинета. ФЛ, ИП и Юрлицо остаются отдельными профилями.

**PROJECT** — внутренний контейнер объекта: тип недвижимости, адрес, площадь, этаж, лифт.

**ORDER** — клиентский заказ. В интерфейсе пользователь видит номер заказа, статус, смету и документы. Расчётный payload пока хранится JSON-снимком внутри заказа, поэтому существующее расчётное ядро не пришлось переписывать.

## Режимы работы

Без `VITE_API_URL` клиент работает автономно на `localStorage`.

С `VITE_API_URL` регистрация идёт через серверный OTP, а профиль и заказы синхронизируются с SQLite.

Такой dual-mode оставляет рабочим текущий прототип и одновременно позволяет развивать сервер без остановки клиентского контура.

## Следующие границы

Для production следующими отдельными модулями должны стать:

- delivery adapter для SMS/e-mail OTP;
- PostgreSQL или управляемая SQL-БД при переходе от одиночного инстанса;
- серверная версия прайсов и коэффициентов;
- документы/договоры;
- платежи;
- аудит изменений заказа;
- роли менеджера и администратора.

Исполнительский контур в этот MVP не входит.


## Версионирование расчёта

Новый заказ получает текущий активный `PRICE_BOOK`. В заказ сохраняются:

- идентификатор, код и версия прайса;
- фактически применённые ставки работ;
- снимок правил образования отходов;
- снимок логистических коэффициентов.

Поэтому публикация v2 не изменяет расчёт заказа, созданного на v1. Для переоценки старого заказа потребуется отдельное явное действие, а не скрытый автоматический пересчёт.


## Документы заказа

`DOCUMENT` связан с конкретным `ORDER` и версионируется независимо по типу документа. Контент документа — неизменяемый JSON-снимок клиента, заказа, сметы и прайса. Изменяются только служебные поля жизненного цикла: статус, дата выпуска и дата подписания.

Это отделяет исторические юридические/коммерческие документы от живого редактируемого заказа.


## Оплаты заказа

`PAYMENT` связан с конкретным `ORDER`. Планируемые платежи резервируют часть остатка заказа; оплаченные платежи уменьшают фактический остаток. Отмена возможна только для запланированного платежа.

Платёжный модуль пока фиксирует финансовый факт внутри Bath Dream и не подключён к эквайрингу или банку.


## Версии, согласование и аудит

После каждого содержательного серверного сохранения `ORDER` создаётся `ORDER_REVISION`, если снимок действительно изменился. Ревизия содержит полный расчётный снимок и краткий diff ключевых полей.

`APPROVAL` фиксирует конкретную ревизию. Подтверждение не пересчитывает снимок и не подменяет его текущим заказом.

`AUDIT_EVENT` фиксирует значимые действия: создание/изменение заказа, отправку версии на согласование и результат согласования.

Таким образом, живой заказ можно продолжать редактировать, а история согласованных состояний остаётся воспроизводимой.
